Cipher = private, group-based commerce + messaging. NOT a public marketplace, exchange, trading terminal, portfolio tracker, social network, shopping cart app, or generic messenger. Four primary destinations, exact order: Chats | Menus | Orders | Profile. Preserve their purpose and navigation behaviour. Eight reference screens: Chats list; individual vendor conversation; long-press message menu; group conversation; Menus (followed vendors + discover); individual vendor menu; Orders overview; Profile/settings. Reference pictures: /home/aegis/aegis-backups/ui-mockups-2026-10-28/ (layout only; where they differ from this spec, THIS SPEC WINS).

## Rules of truth
Inspect the code first. If a feature exists, preserve it and redesign its interface. If partial, keep the supported behaviour. If absent, do not fabricate it, mock successful transactions, invent endpoints, or show fake data as real. No hardcoded sample data in place of real logic. No architecture rewrite for a visual redesign. Uncertainty about behaviour: name it before assuming.

## Brand
Original logo is authoritative (cobalt-blue geometric symbol + bold white wordmark on black; asset in repo, e.g. public/logo.png). Never redraw, distort or approximate it; use the asset where the logo belongs. Name spelling: Cipher. Personality: discreet, confident, premium, precise, modern, technically sophisticated, slightly underground editorial. Understated digital luxury. Not cyberpunk, hacker prop, military dashboard, casino, NFT app.

## Tokens (starting values; small technical adjustments only)
bg #050505 | surface #101010 | surface-2 #171717 | pressed/selected #202020 | border #282828 | separator #1D1D1D | text #F5F6F8 | text-2 #969BA6 | text-3 #707784 | Cipher blue #2463F5 | bright blue (active interaction) #3987FF | success #37C98B | warning #F0B85A | destructive #FF5B64.
Blue is the accent, not a background for every card. No purple/pink/orange/multicolour gradients. Success/warning/destructive reserved for function.
Surfaces: near-black main bg; solid dark cards; borders only to separate adjacent surfaces (do not outline every element); blue backgrounds only for primary buttons, active nav, selected controls, outgoing bubbles; no blue glow on every card; no indiscriminate glassmorphism; no gradients as hierarchy; never reduce contrast for mood; avoid shadows on black.
Type: use the existing typography library (Archivo) if good; one family, consistent weights. Screen headings ~25-30sp semibold/bold; conversation names 14-16 semibold; section labels 11-12 semibold with modest letter spacing; body/message 14-16; metadata 11-12; amounts tabular numerals; buttons 14-15 semibold. Do not uppercase every heading; uppercase only compact section labels. Do not shrink text to unreadable.
Spacing: 4-point scale for screen padding, list padding, card padding, text/metadata gaps, section gaps, icon-label gaps. Breathing room over density; no oversized headers or tall cards.
Corners: small controls/chips 8-12; standard cards 12-16; large transaction cards 14-18; pills only where the shape has a purpose.
Icons: one consistent family already in the project (keep stroke weight and sizes consistent); no emoji as interface icons; no mixing filled/outlined styles randomly.

## Signature elements
A. Cipher blue interaction language: active nav destination, primary actions, outgoing bubbles, selected controls, relevant transaction actions, important active states. Not for every label/icon/border/heading.
B. ONE reusable proprietary transaction-card component, the most carefully designed component: clear container; compact order id/label when supported; item name; quantity/variant/weight when available; agreed price + correct currency; status derived from the ACTUAL order state; progress indicator only where the workflow supports one; the correct next action for the current state; loading, error, completed states. Solid graphite surface, precise type, subtle separators, a clearly identifiable blue primary action. Compact enough to sit inside a conversation. Never show irrelevant actions, fake progress, fabricated timestamps, or payment success without real confirmation. No invented escrow, buyer protection, refunds, arbitration, shipping integrations, guarantees.
C. A small restrained verification indicator ONLY where existing data establishes the group/account is verified. Do not label everyone verified; do not imply a verified group guarantees a safe transaction; do not change what verification means.

## Screens
1 CHATS (primary): title Chats; search action top right if it exists; search field under header; filters All / People / Groups / Orders ONLY those that exist and work; rows: avatar/group image, name, one-line preview, right-aligned timestamp, unread count/indicator, existing pinned/mute indicators; persistent 4-destination bottom nav with Chats selected. Not large cards per row. No recommendations, trending sellers, banners, stories, feeds, carousels. Keep the floating compose button only if it exists today.
2 CONVERSATION: header = back, avatar, name, existing key/verification status, existing actions only (no invented call/video; calls are OFF in this app, so no call icon unless the code actually exposes calls), no exposed keys. Messages: chronological, existing types; incoming = dark graphite bubble, high-contrast text, subtle timestamps; outgoing = Cipher blue, readable, consistent timestamp placement; consistent max width and padding; group consecutive same-sender messages where the model supports it; date separators only where appropriate; bubbles are not bordered shadowed cards. Orders/products render via the reusable transaction card, not obscuring messages. Composer: dark rounded input, clear placeholder, existing attach/text/send only; handle keyboard, safe areas, scrolling, sending state; no unsupported attachment types, payment methods, AI.
3 LONG-PRESS MENU: existing actions only (Reply, Copy, Forward, Delete as supported, plus existing reactions toolbar); only actions valid for that message and permissions; compact dark menu, subtle separators, aligned icons, readable labels, red Delete, no off-screen clipping, proper dismissal; Delete never removes another user's message unless that permission already exists.
4 GROUP: header = back, group avatar, name, accurate member count/subtitle, existing actions; show sender identity for incoming group messages where needed, not repeated on consecutive messages; consistent avatars/bubbles/timestamps; outgoing blue; show the existing verification indicator only if the group is verified; do not invent encryption/permission/moderation claims; same composer as elsewhere.
5 MENUS: not a public marketplace. Keep sections Vendors You Follow and Discover (only as they exist now, same scope and access rules) and the search field and vendor actions. Follow rows: avatar, name, concise update/availability preview, timestamp, new-activity indicator if supported. No trending, recommendations, ads, public reviews, categories. Real vendor data only; no fabricated images/prices/ratings/availability/verification. Bottom nav visible.
6 VENDOR MENU: back; vendor avatar/art; name; existing subtitle/item count; existing overflow only; keep Chat and Following (Chat opens the right conversation, Following reflects real state); no cart or checkout unless it exists; latest-update section with real text and timestamps; compact consistent item rows (existing image or placeholder, name, weight/variant detail, price, currency); no invented attributes; do not turn it into a retail grid.
7 ORDERS: transaction management, not a wallet dashboard. Keep existing grouping/status names (reference: Needs action, In progress, Done, if they match the code's state model; otherwise keep the established terms). Rows: item, details, counterparty, agreed price + currency, status, next valid action; compact rows with section spacing, not big cards. Actions (Pay now, Confirm received, Mark shipped, View receipt) only when valid for the real state and user permission and wired to the existing functions; never fake payment or change status locally without the real confirmation; no tracking, delivery estimates, escrow, disputes, refunds that do not exist. Nav visible, Orders selected.
8 PROFILE: keep the current information architecture and only sections that correspond to real functionality (identity, recovery-key access, wallet balances, privacy, blocked contacts, account details, delivery addresses, backup/recovery). Real configured identity and picture/initials fallback, no hardcoded name. Recovery action findable but visually separate from profile editing. Wallet shows only supported currencies and real balances, formatted correctly, no prices/charts/exchange. Compact settings rows with consistent icons, labels, secondary info, chevrons. Backup shows the REAL status, never claims backed up when not; do not expose secret material unnecessarily. Scrollable on small screens.

## Shared components (build once, reuse)
Screen header, search field, avatar+identity row, conversation list item, message bubble, group sender label, context menu, vendor row, vendor menu item, transaction card, order list row, status indicator, primary/secondary buttons, settings row, bottom navigation.

## Micro-interactions
Clear pressed states; consistent active-tab transition; restrained menu appearance/dismissal; clear send feedback; loading indicators only for real async actions; meaningful status updates only on real state changes; haptics only where already supported; motion never delays actions; honour reduced motion. No fake payment animations, verification animations, glows, particles.

## Quality
Readable contrast; touch targets meet guidance (>=44px); no clipped menus, overlapping text/icons, buttons behind keyboard, content behind system nav, unreadable secondary text, inconsistent scrolling, accidental double submits, layout shift on async updates. Test at real phone widths (320, 360, 375, 390, 412), not just desktop.

## Prohibited unless asked
Public marketplace, public feeds/trending, stories/likes/social engagement, trading charts/portfolio analytics, unsupported coins or payment methods, invented products/users/groups/balances/transactions, invented encryption or verification guarantees, invented order statuses or backend, replacing the 4-tab nav, removing hard-to-redesign features, static mock-ups in place of working screens, redrawing the logo, neon on everything, random gradients, emoji icons, inconsistent radii, changing business logic to simplify visuals, new dependencies without checking existing solutions.
